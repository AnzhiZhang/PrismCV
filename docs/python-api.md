# Python API

PrismCV works with plain Python data. `CV` holds content, languages and design;
`CV.assemble(target, lang)` returns an `Assembled` document for one target and
language, together with a mapping back to the original inputs.

## Basic usage

```python
from prismcv import CV

cv = CV(
    {"header": {"name": "Nathan Lee"}, "sections": {"work": "Experience"}},
    {"languages": {"en": "english"}, "design": {"theme": "classic"}},
    {"job": {"company": "Example", "position": "Engineer"}},
)
target = {"sections": {"work": ["job"]}}
document = cv.assemble(target, "en", literal=True)

rendercv_data = document.to_dict()
yaml_text = document.to_yaml()
issues = document.validate()
typst_source = document.to_typst()
```

`literal=True` keeps prose literal apart from supported Markdown (bold, italic,
links). It is applied during assembly only; the default remains `False`.

## Input data

`CV(cv_yaml, design_yaml, entries)` accepts the same dictionaries as a PrismCV
folder: the header and section titles, design/language settings, and entries
indexed by ID. Targets are passed separately to `assemble()`.

For the portable repository format, `read_files()` accepts a mapping of relative
file names to YAML strings and returns `CVData`. This includes the header,
section titles, languages, design, entries and named targets:

```python
from prismcv import CV, read_files, write_files

data = read_files(files)  # files: dict[str, str]
cv = CV.from_data(data)
target = next(item for item in data.targets if item.name == "industry")
document = cv.assemble(target.data, "en")
exported_files = write_files(data)
```

`CVData`, `Entry` and `Target` can also be constructed directly. Reading or
writing these file mappings does not itself read or write the filesystem.
Invalid portable input raises `FilesError`; assembly errors raise `PrismError`.

## Document methods

| Method | Returns | Behavior |
|---|---|---|
| `to_dict()` | `dict` | Deep copy of the RenderCV document, preserving field and section order. |
| `to_yaml()` | `str` | Readable Unicode YAML, preserving document values and order. |
| `validate()` | `list[Issue]` | RenderCV model diagnostics, with source and document locations. |
| `to_typst()` | `str` | Typst source generated by RenderCV's validated model and templates. |
| `source_of(location)` | `Source` or `None` | Original source of a document location, or its nearest mapped parent. |

The exports do not add CLI output settings or include source mappings in the
document. `to_yaml()` does not write a file. `to_typst()` does not invoke the
CLI, start a subprocess, compile PDF/SVG or write a `.typ` output file.

## Validation and errors

`document.validate()` returns an empty list for valid model input. The existing
top-level `validate(document)` is equivalent. Each `Issue` has a `message`,
`source` (the original input) and `location` (the final RenderCV document).

`to_typst()` validates the input itself; there is no need to call `validate()`
first. Invalid input raises `PrismError` with the same issues:

```python
from prismcv import PrismError

try:
    typst_source = document.to_typst()
except PrismError as error:
    for issue in error.issues:
        print(issue.message, issue.source, issue.location)
```

Template and resource failures also raise `PrismError`. If RenderCV provides no
field location for a failure, its issue has no invented source. Model validation
does not guarantee that the resulting Typst source will compile.

## Editing a document

`document.doc` remains mutable. For example, change the final page size before
generating source:

```python
document.doc.setdefault("design", {}).setdefault("page", {})["size"] = "a4"
typst_source = document.to_typst()
```

Each validation or conversion uses an isolated copy of the current document.
There is no model or source cache, and inputs and source mappings are not
modified by these calls. `to_dict()` also returns an independent copy.

Source mappings refer to the original assembled positions. They do not follow
arbitrary section renaming or entry reordering. Added fields use the existing
nearest-source lookup and may have no source.

## Resources and compilation

Conversion retains RenderCV's resource behavior:

- Remote `cv.photo` URLs may be downloaded to its output folder. Prepare local
  or virtual files first if network access is undesirable.
- Local photo paths are checked relative to the current working directory.
- Custom themes and templates can be loaded from the working directory.
  Custom themes may execute their Python module even during validation.
- Fonts and Typst `@preview` packages are not fetched or checked by source
  generation. The caller supplies them, image resources and a compiler.

The CLI continues to build PDFs and preserve YAML/Typst files with `--debug`.
Browser integrations must supply Python dependencies, RenderCV's bundled
templates, virtual files, fonts, Typst packages and a WASM compiler. Normal
Python tests do not establish Pyodide compatibility; the package still declares
its existing CLI dependencies.
